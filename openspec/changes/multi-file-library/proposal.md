# Proposal: multi-file-library

## Why

当前 App 是「单工作簿工具」：每次只能持有一个导入文件，重新导入即整体覆盖，且用户必须在系统文件选择器的完整目录树里翻找 Excel（真机反馈：内容太多、找不到保存的文件）。需要升级为「多文件库」形态：Excel 导入一次即入库存根，后续从 App 内文件列表直接点开，把「找文件」的成本从每次降到一次。

## What Changes

- **文件库首页（新）**：App 启动即展示已导入文件列表（Excel 图标 / 文件名 / 导入日期 / 删除入口），按导入时间倒序；空态引导导入
- **原生文件选择（升级）**：导入按钮改用原生 `ACTION_OPEN_DOCUMENT` 唤起系统选择器，MIME 类型过滤锁死——所有机型上选择器只显示 Excel 文件（当前 WebView `input[type=file]` 的过滤声明被国产 ROM 无视，真机实测混入截图/PDF）
- **逐文件删除（新）**：文件项左滑展开红色删除按钮（右滑收回，同时仅一项展开），点击弹确认；仅移出 App 库并清理其解析数据，手机上的原文件 MUST NOT 受影响。**不提供全局清空入口**（用户决策）
- **工作簿页（复用）**：点击文件进入现有搜索界面（sheet 下拉/搜索/结果/复制全部复用），顶栏出现返回入口，系统返回键回文件库（而非退出 App）
- **数据模型升级**：IndexedDB 从单工作簿记录改为多文件记录（按 id 索引）；同名文件重新导入覆盖旧版（列表位置保留、日期更新）
- **重启恢复**：恢复到文件库页（不直进上次工作簿）
- **现有「清空导入数据」移除**：不再提供任何全局清空入口，删除文件的唯一路径是逐文件左滑删除

### 明确不做（Non-Goals，源自探索对话的裁剪）

- ❌ 唤起微信选文件（需企业资质 + 小程序 + 文件中转后端，成本倒挂，用户已明确放弃）
- ❌ 悬浮加号按钮、底部弹窗双入口（用户裁剪：保留现有按钮样式）
- ❌ 文件库 App 内搜索（用户裁剪：类型过滤 + 库承接已足够）
- ❌ 微信目录扫描页（随「唤起微信」一并放弃）

## Capabilities

### New Capabilities

- `file-library`: 文件库首页：多文件列表展示、进入工作簿、左滑逐文件删除、空态引导

### Modified Capabilities

- `excel-import`: 「Excel 导入」入口迁移到文件库页；选取改用原生 API 并锁死 Excel 类型过滤；导入结果入多文件库（同名覆盖）；持久化模型从单记录改多记录；取消/失败不影响库内其他文件
- `sheet-switch`: sheet 下拉仅在进入具体工作簿后展示（文件库页无此控件）；进入工作簿自动选中该文件上次选中的 sheet
- `app-packaging`: 安卓返回键行为变更：工作簿页返回键回文件库页，文件库页返回键退出 App

## Impact

- **代码**：`src/composables/useWorkbook.ts`（状态机拆分为 库/工作簿 两层）、`src/services/persistence.ts`（schema v2 多记录 + 迁移）、`src/components/`（新增 FileLibrary/文件项；TopBar 拆分到两视图）、原生 `MainActivity.java` + 新增 FilePicker 插件桥（ACTION_OPEN_DOCUMENT）
- **依赖**：无新增 npm 依赖；原生侧用 Capacitor 自定义插件桥（~80 行 Java）
- **数据迁移**：旧版单工作簿数据自动迁移为库中一条记录（无则空库），用户无感
- **spec 影响**：上述四个能力的主 spec 在归档时同步
